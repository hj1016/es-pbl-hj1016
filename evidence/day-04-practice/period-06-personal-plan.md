## (개인·필수) 문제 1 — 사용자와 판단 하나로 좁히기

Dashboard를 사용할 사람 한 명과 그 사람이 내릴 판단 하나를 정하세요.

### 답안

- 내 주제: DevFix 개발 오류 해결 사례 분석
- 한 문서의 의미: 개발 오류 해결 사례 1건
- 사용자 한 명: 개발 중 오류 해결 사례를 찾는 개발자
- 사용자가 반복해서 하는 일: 오류 유형과 사용 기술을 기준으로 검증된 해결 사례를 찾는다.
- Dashboard를 보고 결정할 것: 우선 검토할 오류 유형과 해결 사례를 정한다.
- 결정 뒤 수행할 행동: 관련 사례의 해결 방법을 확인하고 현재 개발 환경에 적용한다.
- 사용자에게 필요 없는 정보: 데이터 생성 과정의 내부 난수와 Dashboard 판단에 사용하지 않는 원본 부가 정보

`모든 사용자`, `전체 현황`, `데이터를 본다`처럼 넓은 표현은 한 사람과 한 행동으로 좁힙니다.

## (개인·필수) 문제 2 — 서로 중복되지 않는 질문 4개

다음 역할을 하나씩 사용해 질문 4개를 작성하세요.

1. 전체 규모
2. 그룹 비교
3. 수치 분포 또는 정확한 값 비교
4. 상태 비율 또는 시간 변화

| 번호 | 분석 질문 | 질문의 답으로 내릴 판단 | 다른 질문과 겹치지 않는 이유 |
|---|---|---|---|
| Q1 | 전체 오류 해결 사례는 몇 건인가? | 분석할 수 있는 데이터 규모가 충분한지 판단한다. | 전체 규모만 확인한다. |
| Q2 | 어떤 오류 유형과 기술의 사례가 많은가? | 우선 탐색할 오류 유형과 기술을 정한다. | 범주별 사례 수를 비교한다. |
| Q3 | 해결 시간은 어느 구간에 몰려 있고 기술별 평균은 어떤가? | 짧은 해결 사례를 우선 볼지, 특정 기술을 더 확인할지 정한다. | 숫자 분포와 정확한 평균을 비교한다. |
| Q4 | 검증된 사례 비율과 월별 등록 분포는 어떤가? | 검증 상태를 확인하고 등록 시점별 문서 분포를 파악한다. | 상태 비율과 시간 변화를 확인한다. |

## (개인·필수) 문제 3 — 질문별 field 존재 여부 점검

각 질문에 필요한 field가 실제 mapping과 문서에 있는지 확인하세요.

| 질문 | 필요한 field | mapping type | 실제 존재 | 값이 충분히 분포 | 가능/가공 필요/추가 필요 |
|---|---|---|---|---|---|
| Q1 | `case_id` | `keyword` | 예 | 50,000개 문서 | 가능 |
| Q2 | `error_category`, `technology` | `keyword`, `keyword` | 예 | 각각 6개 범주 | 가능 |
| Q3 | `resolution_minutes`, `technology` | `integer`, `keyword` | 예 | 5~240분, 기술 6개 | 가능 |
| Q4 | `verified`, `created_at` | `boolean`, `date` | 예 | true/false 및 2025-01~2026-08 | 가능 |

- 현재 데이터로 바로 만들 수 있는 질문 수: 4개
- 선택한 A/B/C 경로: A 개인 데이터 사용
- 선택 이유: `devfix-cases`에 50,000건이 있고 네 질문에 필요한 범주·수치·상태·날짜 field가 모두 존재한다.

## (개인·필수) 문제 4 — 부족한 데이터 생성 규칙 설계

현재 답할 수 없는 질문 하나를 선택하고 필요한 데이터를 구체화하세요.

- 답할 수 없는 질문: 장애 심각도별 SLA 준수율은 어떠한가?
- 부족한 field: `severity`, `resolved_at`, `sla_met`
- mapping type: `keyword`, `date`, `boolean`
- 예시값 3개: `P1`, `P2`, `P3`
- 범주라면 고유값 수: `severity` 4개(`P1`~`P4`)
- 수치라면 최소·최대·대표 구간:
- 상태라면 예상 비율: `sla_met=true` 85%, `false` 15%
- 날짜라면 기간과 단위: 기존 `created_at` 기간과 같은 2025-01~2026-08, 월 단위
- 다른 field와 필요한 관계: `resolved_at`은 `created_at` 이후이며, 심각도별 SLA 기준 시간과 실제 소요 시간을 비교해 `sla_met`를 결정한다.
- 한 문서를 생성하는 규칙: 심각도를 P1~P4 중 하나로 배정하고 `created_at` 이후의 `resolved_at`을 만든 뒤, 심각도별 기준 시간 이내이면 `sla_met=true`로 기록한다.
- 필요한 문서 수와 이유: 기존 50,000건 전체에 값을 추가해 심각도별 비교에 충분한 표본을 유지한다.
- seed 고정 여부: `20260901`로 고정
- 생성 후 검증 방법: mapping 확인 후 심각도별 문서 수, SLA 상태 합계, 날짜 선후 관계와 전체 50,000건 일치 여부를 집계한다.

“랜덤으로 많이 만든다”는 규칙이 아닙니다. Dashboard에서 비교·분포·필터 결과가 나타나도록 값의 범위와 관계를 적습니다.
